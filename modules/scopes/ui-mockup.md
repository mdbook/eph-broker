## Scope: UI changes are built from the mockup and checked by eye
A ticket is a **UI change** when it adds or changes anything a person sees: an HTML/CSS/JS view, a template, a page, a component, or markup and styles embedded in code (for example a page held in a source string). For a UI change these rules are part of the ticket, whatever the ticket's wording:

- **Find the mockup first.** It is the file or directory the ticket names or links, or one already in the repo for this screen (look for a `mockups/` directory, `docs/mockups/`, or a path the ticket or a linked ticket cites). It is the design. Your build follows it; you do not re-interpret it.
- **No mockup, no build.** If a UI ticket names no mockup and none exists in the repo for this screen, do NOT invent the design. Change nothing, commit nothing, and return `status:"blocked"` with `needs_operator: true`, saying the ticket needs a mockup (file or path) before it can be built. The broker posts that as the ticket comment and opens no MR.
- **Port, do not paraphrase.** Copy the mockup's markup structure and CSS into the real code (adapted to the repo's templating, names and data), rather than writing your own version of the same idea. Keep its layout pattern (for example a transcript of rows stays a transcript, never chat bubbles), alignment, element order, and every region it shows (header, navigation, composer, footer, empty and error states).
- **Render both.** Render the mockup AND your build with a real browser at every viewport the ticket names; when it names none, use 1440x900 (desktop) and 390x844 (mobile). Use the Playwright browser tools in your grant (navigate, resize, take screenshot), or a screenshot script the repo already runs through your granted test runner. Save the PNGs inside your worktree, in the screenshot directory the ticket names, else the repo's existing screenshot directory, else `docs/screenshots/ticket-<id>/`, named so each pair sits side by side: `mockup-<width>x<height>.png` and `build-<width>x<height>.png`.
- **Look at them.** Open every PNG with your file-read tool (in Claude Code, `Read` on a `.png` shows you the image) and compare each mockup/build pair before you commit. A structural difference (layout pattern, alignment, element order, a missing or extra region) is a bug: fix the build and re-render until the pairs match. A **minor deviation** may stay when it has a valid reason (contrast, tap-target size, spacing forced by real data, a platform constraint, accessibility): list each one in your summary, which becomes the MR description, with its reason. An unlisted deviation reads as a mismatch. Differences that come only from placeholder data versus real data are fine; name them.
- **Commit the screenshots** with the change (this overrides the "keep verification evidence out of the commit" default), and list every PNG path, mockup and build per viewport, in your summary, which becomes the MR description. Say in the summary that you opened and compared each pair, and name any difference you left and why.
- **If you cannot render or cannot view an image** (no browser tool in your grant because the ticket was not routed to the broker's UI code row, the page will not load, or your harness cannot show images), that is an environment gap: commit the code change, say exactly which screenshots are missing and why, and never claim you viewed an image you did not open. The reviewer blocks a UI MR without screenshots, so the gap must be stated plainly.
